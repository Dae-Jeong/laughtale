# Application — 업무 흐름

읽는 때: Service, Facade, Validator, Job의 업무 흐름·입출력을 변경할 때 읽습니다.
공통 기준과 문서 선택은 [개발 규칙 진입점](../engineering-principles.md)을 따릅니다.

## Service와 내부 계약

- Service는 use case의 검증, Domain 상태 변경, 영속화 순서를 조정합니다. SQL을 직접 작성하거나 다른 도메인의 Repository로 그 도메인의 데이터를 변경하지 않습니다.
- 다른 도메인의 데이터는 소유 도메인의 조회 계약으로 가져옵니다. 도메인 간 순환 Service 호출을 만들지 않습니다.
- HTTP 응답·ORM 객체 대신 명시적인 내부 타입으로 결과를 표현합니다. 결과가 없는 작업은 반환값 없이 종료할 수 있으며, 단순 값에 빈 DTO나 중복 wrapper를 만들지 않습니다.
- 구조화된 결과가 필요하면 Internal DTO를 사용합니다. Python에서는 불변 dataclass를 기본으로 하며 값과 순수 변환만 담습니다. `from_entity()`는 이미 확보한 내부 모델을 변환하고 I/O를 실행하지 않습니다.
- 복잡한 매핑·오류 번역은 의미 있는 협력 함수나 모듈로 분리하고 업무 검증을 그 안에 숨기지 않습니다.

## Facade

- 여러 Service를 조합하는 use case의 실행 순서와 실패 처리를 소유합니다. 단일 Service 호출만 있는 기능에는 추가하지 않습니다.
- Service를 거치지 않고 Repository에 직접 접근하거나 다른 Facade를 중첩 호출하지 않습니다. 조합이 반복되면 업무 소유권과 경계를 다시 검토합니다.

## Validator

- 다른 엔티티 조회가 필요한 존재·소유권·한도 같은 사전 조건을 검증합니다. 재사용하거나 분리할 검증 책임이 있을 때만 별도로 둡니다.
- 상태를 변경하거나 트랜잭션을 시작하지 않습니다. 입력 Schema의 형식 검증이나 Domain이 소유한 불변조건을 복제하지 않습니다.

## Job

- 예약 실행과 작업 단위별 실패 격리를 담당하며 Service/Facade를 호출합니다. DB·외부 API 직접 접근이나 업무 규칙 구현은 하지 않습니다.
- 다른 Job 호출로 업무 흐름을 만들지 않습니다. 중복 실행·재시작·누락 실행·항목별 실패 정책을 정하고 같은 use case를 다른 진입점에서도 재사용합니다.

## 함께 읽을 조건

- 상태 전이·업무 정책을 바꾸면 [Domain](domain.md)을 읽습니다.
- DB를 사용하거나 여러 변경의 성공·실패 범위를 정하면 [트랜잭션](persistence.md#트랜잭션과-외부-실행)을 읽습니다. 원자성 기준은 그 절이 소유합니다.
- 외부 API·SDK를 호출하면 [외부 연계](external-integrations.md)를 읽습니다.
- 구현·검증 시에는 [Testing](testing.md)을 읽습니다.
