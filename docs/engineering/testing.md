# Testing — 완료를 증명하는 검증

읽는 때: 코드 구현·테스트·완료 판정을 하거나 검증 기준을 리뷰할 때 읽습니다.
공통 기준과 문서 선택은 [개발 규칙 진입점](../engineering-principles.md)을 따릅니다.

## 검증 대상별 증거

| 대상 | 확인할 내용 |
| --- | --- |
| Domain·정책 | 외부 I/O 없이 업무 결과, 허용·금지 상태 전이와 불변조건을 검증합니다. |
| Service·Facade | Port 대역으로 업무 흐름과 부분 실패를 확인합니다. 응답뿐 아니라 DB 변경·미변경, 외부 호출 횟수 등 해당 위험을 증명하는 결과를 확인합니다. |
| Repository·트랜잭션 | 실제 테스트 DB에서 제약·쿼리·commit·rollback을 검증합니다. 선점·한도 기능은 중복 요청·동시 실행에서도 불변조건을 지키는지 확인합니다. |
| HTTP API | status·입출력 DTO·오류·pagination 계약을 검증합니다. |
| 외부 Adapter | 응답 fixture로 값·Enum·오류 변환, 누락·비정상 응답 처리를 검증합니다. |
| Client | 격리된 HTTP/SDK 대역으로 인증 설정·timeout·재시도 상한·취소·종료를 검증합니다. 쓰기는 중복 요청·응답 유실 후 재시도에서 효과가 중복되지 않는지 확인합니다. |

## 실행과 격리

- 시간과 외부 의존성을 제어해 실패를 재현합니다. 테스트가 구현을 그대로 반복하거나 실행 순서·숨은 공유 상태에 의존하지 않게 합니다.
- 테스트 DB·환경은 개발·운영 데이터에서 격리하고 실행 전에 대상을 확인합니다. 병렬 테스트는 데이터 충돌이 없도록 분리합니다.
- fixture와 필요한 factory/Mother에는 유효한 기본값과 명시적인 변경값을 제공합니다.
- 기본 테스트는 외부 API를 대역으로 검증합니다. 실제 provider 계약 검증은 별도 sandbox smoke로 구분하고 대상 계정·비용·데이터 영향·권한을 확인합니다. 기본 테스트에서 실거래를 호출하지 않습니다.
- 대역 테스트가 통과한 것과 provider가 실제 보장하는 범위를 구분합니다. 반복된 오류는 가장 좁고 재현 가능한 회귀 검증으로 남깁니다.
- 실패한 테스트를 통과시키려고 요구사항을 조용히 완화하지 않습니다. 요구가 바뀌면 근거와 기대 결과를 먼저 갱신합니다.
- 실제 설정된 lint·type check·test와 필요한 빌드를 실행합니다. 아직 없는 doctor나 실행하지 않은 검사를 통과했다고 보고하지 않습니다.

## TDD 적용 상태

TDD는 조사·실험 후보이며 현재 의무 개발 방식이 아닙니다. 설치된 설계 스킬이 TDD 스킬을
후속 단계로 지시하더라도 자동 적용하거나 설치하지 않습니다. 이 프로젝트의 현재 검증 기준은
위 내용이며, 테스트 작성 순서의 의무화는 별도 승인 후 변경합니다.

## 함께 읽을 조건

성능·부하·용량 검증의 가설·실험 조건·판정은 [Runtime Review](runtime-review.md)를 함께 읽습니다.
지표 수집·집계·경보·자동 확장 검증은 [Metrics](metrics.md)를 함께 읽습니다.

검증 대상의 기대 동작이 불명확하면 [진입점의 소유 문서 표](../engineering-principles.md#작업별-선택-읽기)에서
해당 책임의 문서만 추가로 읽습니다. 테스트 목적만으로 모든 역할 문서를 펼치지 않습니다.
